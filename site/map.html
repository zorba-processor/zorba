The big picture

XQuery and JSONiq are easy to underestimate. They look like path expressions with some loops, but they are complete functional languages over one data model, with optional layers for updates, text search, side effects and storage. This page lays out the whole map before the tutorials go into detail.

The idea in one paragraph

Every value is a sequence of items. An item is an atomic value (a number, a string, a date), a node of an XML tree, a JSON object or array, or a function. Every construct of the language is an expression that takes sequences and returns a sequence, so expressions nest freely: a path can appear inside a loop, a loop inside an element constructor, a constructor inside a function argument. XPath is the sublanguage for navigating trees; XQuery adds variables, loops, sorting, grouping, constructors, functions and modules; JSONiq adds JSON. Extensions add updates, full-text search, imperative scripting and persistent collections.

Everything is a sequence

A sequence is an ordered list of zero or more items. Three rules explain most of what surprises newcomers:

  • Sequences are flat. A sequence never contains another sequence. Writing (1, (2, 3)) gives the three-item sequence (1, 2, 3). To nest, you need a structure: an XML element or a JSON array.
  • One item is a sequence of length one. There is no difference between 42 and (42), so functions that "return a value" and functions that "return a list" are the same thing.
  • The empty sequence () stands for "nothing". A path that matches nothing returns (), and most functions given () return () rather than failing.

Why it matters: the first number is the count. Flattening is why you can concatenate results with a comma without worrying about levels of nesting.

Why it matters: there is no separate "scalar" and "list" world. Predicates like [1] work on any value, and count, empty and friends are the way to ask how many items you have.

Four kinds of items

Atomic values
Typed scalars. The types come from XML Schema: xs:string, xs:integer, xs:decimal, xs:double, xs:boolean, xs:date, xs:dateTime, xs:duration, xs:QName and a few dozen more. Decimal arithmetic is exact; dates and durations have real arithmetic.
Nodes
The parts of an XML tree: document, element, attribute, text, comment, processing instruction and namespace nodes. A node has an identity and a position in its tree, so it has a parent, children and siblings.
JSON items
Objects (unordered string-keyed maps) and arrays (ordered lists whose members can be sequences of any length, flattened when you take them out). JSONiq adds them to the data model, together with the atomic value null.
Function items
Functions as values (XQuery 3.0): named function references like upper-case#1, inline functions, and partial applications. They are what makes for-each, filter and fold-left possible.

Why it matters: typeswitch and instance of work uniformly across every kind of item, which is how one query handles XML and JSON input with the same code.

Nodes and values

A node is not its text. When an operation needs a value (arithmetic, comparison, a function that takes a string), the node is atomized: its typed value is extracted. Without a schema, the typed value of an element is xs:untypedAtomic, which converts to whatever the context needs, so price * 2 just works. With a schema (see types), atomization yields properly typed values.

Nodes also have identity: two elements with the same content are equal by value (deep-equal) but are not the same node (is).

Why it matters: most "why did my comparison fail" puzzles are about atomization or identity. Keep the two ideas apart and the language becomes predictable.

Null and the empty sequence

XQuery has no null. "No value" is the empty sequence, and it propagates: () + 1 is (). JSON needs a real null because {"coupon": null} and {} are different documents. JSONiq therefore has both, and they mean different things:

  • null is an item. A sequence containing it has length one.
  • Looking up a key that does not exist returns (), length zero.

Why it matters: you can tell "explicitly null" from "absent" in a JSON document, which most JSON query tools blur. The JSONiq page shows how this plays out in queries.

Expressions, not statements

A query is one expression whose value is the result. There are no statements to sequence and no variables to reassign: let binds a name to a value once, if returns a value, and a for loop returns the concatenation of what each iteration returns. This is what lets a query nest a loop inside an element constructor inside a function call.

The absence of side effects is also what makes queries optimizable: Zorba can reorder, inline and rewrite expressions. Updates and scripting, described below, are carefully specified exceptions.

XPath inside XQuery

XPath is the expression language for addressing parts of a tree: //book[@lang = "es"]/title. XQuery 1.0 was defined as XPath 2.0 plus a prolog (declarations of namespaces, variables, functions and modules), FLWOR expressions, node constructors and a type system. XQuery 3.0 extends XPath 3.0 the same way. As a result, every XPath 2.0 or 3.0 expression is already a complete XQuery query:

Why it matters: if you have used XPath in a browser, in XSLT or in an XML library, you already know the navigation part of XQuery.

XPath 1.0, the version most libraries still ship, has no sequences (it has node-sets), only four data types and no conditional or loop expressions. XQuery is built on the 2.0 model and later.

The deeper difference is the data model: SQL rows are flat and typed by a fixed schema; XQuery items can be trees of any depth, and a schema is optional.

XQuery and XSLT

XSLT 2.0 and 3.0 share XPath, the data model and the function library with XQuery. They differ in style: XSLT is organized as template rules that fire on the nodes of the input (push processing), while XQuery is organized as expressions that pull the data they need. Document-to-document transformation with many small rules tends to read better in XSLT; querying, joining and building new structures tends to read better in XQuery. Zorba runs XQuery and JSONiq only; it does not execute XSLT stylesheets.
