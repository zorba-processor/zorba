XQuery

From a path expression to grouping, windows, updates and text search. Each section is short: an idea, an example run by Zorba, its output, and why it is worth knowing.

The sample data

Most examples read the same small file. doc() loads and parses an XML document; relative paths resolve against the location of the query file.

Paths

A path is a series of steps separated by /. Each step selects nodes relative to the nodes selected by the previous step. // means "at any depth". The result comes back in document order, without duplicates.

Why it matters: a path returns nodes, not strings. The titles above are still elements that you can navigate further or copy into new documents.

Predicates

Square brackets filter. A boolean predicate keeps the items for which it is true; a number selects by position, starting at 1. Predicates can be chained and can contain paths of their own.

Why it matters: //book[2] means "each book that is the second book child of its parent", while (//book)[last()] takes the last item of the whole sequence. The parentheses change the meaning.

Axes

A step moves along an axis. child:: is the default and @ abbreviates attribute::. Others go up (parent::, written .., and ancestor::), sideways (following-sibling::, preceding-sibling::) or down (descendant::).

Why it matters: you can start from the node you found and move in any direction, instead of restructuring the query to come from the top.

From nodes to values

Aggregates and string functions atomize their input. A function call can be a path step (price/xs:decimal(.)), and the simple map operator ! applies an expression to each item of a sequence, with . bound to the item.

Why it matters: converting with xs:decimal gives exact decimal arithmetic. Summing the untyped values directly would convert them to xs:double, with binary rounding.

Comparisons and quantifiers

There are two families of comparison. General comparisons (=, !=, <, >, ...) compare sequences and are true if any pair of items matches. Value comparisons (eq, ne, lt, gt, ...) compare exactly one item with one item and raise an error otherwise. some and every quantify explicitly.

Why it matters: $books/@lang = "en" reads like an equality test but means "at least one book is in English". Use eq when you expect a single value and want to be told if you get several.

FLWOR

The FLWOR expression (pronounced "flower") is the workhorse. for iterates, let binds a value, where filters, order by sorts and return builds the result for each surviving binding.

Why it matters: the clauses can repeat and appear in almost any order, so a FLWOR covers what SQL spreads across SELECT, FROM, WHERE, ORDER BY and subqueries.

Grouping

group by (XQuery 3.0) partitions the bindings by a key. After the clause, every other variable holds the sequence of values from its group, so count($b) counts the books of each author and sum($price) adds their prices.

Why it matters: before 3.0 this needed distinct-values plus a nested query per key. Now it is a single clause.

Positions and ranks

for $x at $pos binds the position of each item in the input sequence. The count clause numbers the bindings at the point where it appears, so after order by it gives a rank.

Why it matters: the two numbers answer different questions: where the item was in the input, and where it is in the result.

Joins

Two for clauses form a join; the predicate or where is the join condition. allowing empty keeps an outer binding even when the inner sequence is empty, like a left outer join.

Why it matters: joins work across documents and sources, not only across tables of one database.

Windows

A window clause slides over a sequence and binds a whole sub-sequence at a time. A tumbling window starts a new window after the previous one ends; a sliding window starts one at every position that meets the start condition. only end drops windows whose end condition never became true.

Why it matters: batching, sessions in logs and moving averages over time series become declarative.

Constructors

Direct constructors write XML literally. Curly braces inside content or attribute values evaluate an expression and insert its result.

Computed constructors build nodes whose names are themselves computed.

Why it matters: output is built as a tree, so it is always well formed, and characters such as < and & are escaped by the serializer.

Functions

Functions are declared in the prolog, before the query body. Functions in a main module go in the local namespace. Parameter and return types are optional; when present, arguments are checked and converted.

Why it matters: recursion is the natural way to walk trees of unknown depth, and typed signatures catch mistakes early.

Functions as values

XQuery 3.0 has function items: inline functions (function($x) { ... }), named references (upper-case#1, where the number is the arity) and dynamic calls ($f(3)). The standard library has the usual higher-order functions.

Why it matters: behaviour can be passed as a parameter, which makes generic library functions possible.

Modules

A library module declares a target namespace and contains functions and variables in it. A main module imports it with import module namespace; the at clause gives its location.

Why it matters: modules are how code is shared, and how Zorba's built-in libraries are exposed (see built-in modules).

Strings, numbers, dates

The standard function library includes regular expressions (matches, replace, tokenize, analyze-string) and, since 3.0, formatting of numbers and dates. The || operator concatenates strings.

Why it matters: most text munging needs no extension library.

Types and casting

Every atomic value has a type. Constructor functions like xs:date("...") and cast as convert; castable as tests without failing; instance of checks the type of a value. Integer division with div gives an exact decimal; with doubles you get binary floating point.

switch selects by value, typeswitch by type (see the item kinds example).

Why it matters: dates, durations and decimals behave like values with arithmetic, not like strings you have to parse again.

Schema validation

With an XML Schema imported, validate checks a node and annotates it with types. Atomizing a validated element then gives typed values: here xs:positiveInteger and xs:decimal instead of untyped text. Invalid input raises err:XQDY0027.

Why it matters: input checking and typing come from the schema you already have, not from hand-written checks in every query.

Errors

Errors are identified by QNames. try/catch (XQuery 3.0) catches them by name, by namespace wildcard or with *; inside the catch, variables such as $err:code and $err:description describe the error. error() raises your own.

XQuery 3.0 says the err prefix is predeclared. In Zorba some catch clauses fail with XPST0081 ("can not expand prefix") unless the prefix is declared, so the examples on this site declare it explicitly. The declaration is valid in any processor.

Why it matters: failures in one part of a result, such as a malformed date in one record, can be handled without aborting the whole query.

Updates

The Update Facility adds expressions that change nodes: insert node, delete node, replace node, replace value of node and rename node. Changes are collected into a pending update list and applied together at the end, so expressions never see a half-updated tree. copy/modify/return applies updates to a copy and returns it.

Why it matters: "the same document with a few changes" is one expression instead of a full rebuild. To make changes persist across statements, apply them to nodes in a collection or use scripting.

Full-text search

contains text searches the words of a node, not its characters: it tokenizes the text, ignores case by default and can apply stemming, wildcards, stop words and thesauri.

Searches combine with ftand, ftor and ftnot, and can be restricted by distance or window.

Why it matters: "fox" does not match "Foxes" as a substring test would, but it does with stemming. Word-aware search is part of the query language instead of a separate engine.
