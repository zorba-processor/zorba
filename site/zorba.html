Using Zorba

The parts of Zorba that are not the language itself: how to run queries, which libraries ship with it, the in-memory store, and the C++ API.

The command line

zorba runs one or more queries and writes the results to standard output. A query is either given inline or, with -f, read from a file. A .jq file is parsed as JSONiq; anything else as XQuery unless -j is given.

OptionEffect
-q <query>The query text, or a file name with -f.
-f, --as-filesTreat the -q arguments as file names.
-i, --indentIndent the output.
-r, --omit-xml-declarationDo not print <?xml ...?>.
-j, --jsoniqParse the query as JSONiq whatever its extension.
-e name:=valueBind an external variable to a string; -e name=file binds it to the parsed XML document in a file.
--context-item <file>Make the XML document in a file the context item.
-z name=valueSet a serialization parameter, for example -z method=json or -z method=xhtml.
--serialize-text, --serialize-htmlShortcuts for the text and HTML output methods.
-o <file>Write the result to a file.
--module-path <dirs>Directories to search for imported modules.
--base-uri <uri>Set the static base URI used to resolve relative paths.
-t, --timingPrint compilation and execution times.
--compile-only, --parse-onlyCheck a query without running it.

zorba --help lists everything, including optimizer and debugging switches. By default the output method is json-xml-hybrid: XML nodes are serialized as XML, JSON items as JSON, and atomic values separated by spaces, which is what you see in the examples on this site.

Restricting a query

By default zorba trusts the query: it may read and write files, use the network, read environment variables, expand external entities in XML input and load modules implemented in C++. To run a query you do not trust, start from --secure, which allows none of that, and allow only what the query needs. The capabilities are external-entities, file-read, file-write, network, remote-import (module and schema import over the network), environment, native-modules (for example the file and http-client modules) and all.

OptionEffect
--secureStart from a policy that allows no capability.
--allow <caps>, --deny <caps>Allow or deny a comma-separated list of capabilities, applied in command-line order.
--read-path <dir>, --write-path <dir>Limit file reads or writes to a directory (repeatable).
--network-prefix <url>Limit network access to URLs under a prefix (repeatable).
--private-addresses allow|denyWhether the network capability reaches loopback, private and link-local addresses; denied by default with --secure.
--timeout <s>, --max-call-depth <n>Stop the query after a time (zerr:ZXQP0068) or a function call depth (zerr:ZXQP0069).
 
zorba --secure --allow file-read --read-path /srv/data --timeout 10 -f -q report.xq

A denied file or network access raises zerr:ZXQP0029, and importing a module that needs a denied capability raises zerr:ZXQP0067; denied environment functions return the empty sequence. Modules and schemas in the URI and library paths (which include the current directory) can always be imported. The files named on the command line (queries, --context-item, -e name=file, -o) are opened by zorba itself and are not restricted.

Why it matters: a query from a user, a request or a file you did not write cannot read /etc/passwd, reach an internal service or run forever.

External variables

A query declares the inputs it expects with declare variable ... external, optionally with a type and a default. The command line or the C++ API supplies the values.

Why it matters: a query becomes a reusable program with parameters instead of a string you edit.

Collections

A collection is a named, ordered set of documents or JSON items kept in Zorba's store for the life of the process. The dynamic collection modules create collections by QName at run time; the data manipulation functions insert and delete whole items. These are updating functions, and in a program with several statements (see scripting) each statement's updates are applied when it ends.

Why it matters: dml:delete is needed because the items of a collection are roots. The Update Facility's delete node has no effect on a node without a parent.

Static collections and indexes

XQDDF, Zorba's data definition facility, declares collections, indexes and constraints in the prolog of a library module, much as SQL DDL declares tables. A declared collection has a type, and a declared index is maintained by the store as the collection changes.

Why it matters: an index probe finds the matching items without scanning the collection. Zorba does not choose indexes automatically: you probe them by name, as above.

Integrity constraints

Integrity constraints declared on a collection are checked when updates are applied, once activated. Here the second insert of the same sku violates a unique key, the whole update is rejected, and the collection keeps one product.

Why it matters: invariants live next to the data definition instead of being re-checked by every query that writes.

Scripting

Zorba's scripting extension adds imperative constructs to XQuery and JSONiq: statements separated by semicolons, mutable variables declared with variable, assignment with :=, blocks in braces, while loops, exit returning, and functions annotated %an:sequential that may have side effects. The updates of each statement are applied before the next one runs.

Why it matters: programs that create collections, load data, update it and then query it can be written in one file, as in the collection examples above.

break and continue are not implemented inside FLWOR expressions; use while loops when you need them.

Embedding in C++

The C++ API is in include/zorba. The usual pattern: create a store and a Zorba instance, compile a query into an XQuery object, bind external variables on its dynamic context, iterate over the result, and shut down in reverse order. Compilation errors and runtime errors are thrown as ZorbaException. This program is compiled against the installed headers and linked with libzorba_simplestore as part of the site build.

Unlike the command line, an embedded engine starts from the secure policy: queries cannot read or write files, use the network, expand external entities, load native modules or read environment variables until the application allows it, for example engine->setSecurityPolicy(SecurityPolicy::secure().allow(Capability::FileRead).addReadPath("/srv/data")). engine->setSecurityPolicy(SecurityPolicy::unrestricted()) restores the behavior of Zorba 4.x. The policy is declared in include/zorba/security.h.

Why it matters: a compiled query can be executed many times with different variables, which is how an application uses Zorba as its query engine. More examples are in doc/cxx/examples.

Threading

Zorba 5.0 is not thread-safe, and there is one engine and one store per process (Zorba::getInstance returns a singleton). Use Zorba, and every object created from it, from one thread at a time; if several threads need it, serialize all calls with your own mutex. For parallel queries, run separate processes. Making the engine thread-safe is planned for a 5.x release.

Limits

  • The store is in memory and not persistent: collections disappear when the process ends.
  • No XQuery 3.1 (maps, arrays, =>, ?). Use JSONiq.
  • Full Text is mostly, not completely, implemented; serialization character maps are not implemented.
  • XQueryX needs a build with ZORBA_XQUERYX enabled.
  • No XSLT.

The source, the issue tracker and build instructions are in the GitHub repository.
